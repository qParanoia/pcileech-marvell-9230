# First independent RAM stage

`firmware/startup.s` is a standalone ARM-state entry stage. It contains its
own exception vectors, supervisor and IRQ stacks, UART setup, a chip-ID read,
and an IRQ handler that records pending bits and increments a counter in RAM.
It does not call the vendor firmware.

Check the stage entirely offline:

```text
python tools/emulate_startup.py ../88.bin
```

The check assembles the source, places it at RAM address zero in a temporary
image, runs it in Unicorn, injects one synthetic IRQ, and verifies UART,
markers, stack restoration, and return to the idle loop. The expected output
starts with `OPEN9230 STAGE0` and `CHIP=92301B4B`.

A local experimental image can be built with:

```text
python tools/build_startup.py --template ../88.bin --output build/startup.bin
```

The resulting image is **hybrid**: it still uses the stock SPI autoload,
loader, Option ROM, and unused vendor segments. The open entry stage is 376
bytes in CODE1. This image does not initialize SATA or PCIe, and its IRQs
remain masked after setup. It is an emulator and bring-up artifact, not a
replacement firmware for a disk-bearing system.

## Freestanding C stage

Arm GNU Toolchain 15.2.Rel1 for Windows (AArch32 bare metal) is installed
portably at `build/toolchain/`. The downloaded archive is ignored by Git. Its
SHA-256 is `7936cac895611023ffb22a64b8e426098c7104cb689778c1894572ca840b9ece`,
which matches the checksum published next to the archive by Arm. The pinned
archive URL is
`https://armkeil.blob.core.windows.net/developer/files/downloads/gnu/15.2.rel1/binrel/arm-gnu-toolchain-15.2.rel1-mingw-w64-x86_64-arm-none-eabi.zip`.
On another Windows checkout, `powershell -File tools/setup_toolchain.ps1`
downloads, verifies, and extracts the same version into `build/`.

Build and verify the C stage:

```text
python tools/build_c_stage.py --template ../88.bin --output build/c-stage-v6.bin
python tools/emulate_c_stage.py ../88.bin
```

`crt0.S` supplies vectors, mode stacks, BSS clearing, and the IRQ entry.
`stage.c` runs UART and the IRQ handler. It first prints a read-only snapshot of
all four physical-port link states and signatures plus PUNIT registers
`0xD0020110`, `0xD0020114`, `0xD0020300`, and `0xD0020318`. These readings
distinguish the state left by the SPI loader from the state reached after
initialization. The first hardware run of C-stage v1 confirmed physical
port-0 link/signature reads, but IDENTIFY timed out with `CI=1`, `IS=0`,
`TFD=0x150`. Its entry PUNIT control words were all zero. See the exact
[board captures](hardware-baseline.md).

C-stage v2 added the independently written `punit_init.c`, based on the
observed register sequence at reference IDA `0x5FD30`, enabled the backend
controller at `0x8000A804`, and reported PUNIT/backend and port-0 state after
initialization. Its board run reached the IDENTIFY issue code but stopped
mid-line while printing `P0_IDENTI`. The board did not restart. This might
be an interrupt problem, but the log does not prove that the command
completed. Register `0xD0020110` read back as zero despite a write of `0xF`;
the Unicorn fixture now models that observed readback without assigning it a
hardware meaning. The stock PUNIT interrupt callback is omitted because the
open handler does not yet support that event. `sata_port0.c` reads backend
port count, port-0 link status, and ATA signature. When the link and
signature indicate an ATA device, it constructs an IDENTIFY command
descriptor byte-for-byte equal to the one generated by stock code in the
same Unicorn fixture, programs port-0 registers including the observed
extended base at `0x8000A970`, and issues slot 0. C-stage v3 kept both CPU
and port-0 IRQs masked and polled the command issue bit. It initialized the
IDENTIFY buffer to `0xA5` so a reported word 0 of `0xA5A5` would reveal that
no data was written. On the board, `CI` cleared and the SRAM buffer contained
valid ATA IDENTIFY words: word 0 `0x40`, major version `0x07F8`, rotation `1`,
and DATA SET MANAGEMENT `1`. The port interrupt status was `2`, task-file
status `0x50`, and global IRQ status zero. This establishes one real
read-only physical-port command and DMA path with polling. The UART prints
`P0_IDENTIFY_START` before touching the command registers and
`P0_IDENTIFY_ISSUED` immediately after the command write, or
`P0_IDENTIFY_SETUP_FAIL` if the command engine does not accept the start bits.
A bounded polling loop reports progress and then port-0 `CI`, `IS`, `TFD`,
command control, extended base, backend control, and global interrupt status
if completion never arrives. The offline check also exercises that timeout
with a shorter compile-time threshold.

C-stage v4 used the same polling path to issue a read-only `READ DMA EXT`
(`0x25`) of LBA 0 in slot 1. Its command slot and request table match the
first stock READ DMA EXT request byte-for-byte in the Unicorn SSD run. The
512-byte destination was initialized to `0xA5`. On the board, slot 1 retired,
`PxIS=1`, `PxTFD=0x50`, and 504 of the 512 bytes inspected changed. The first
eight bytes were still `0xA5`, revealing that the tagged pointer
`0x0006E0D9` actually addresses `0x3006E0D8`; v4 inspected from
`0x3006E0D0`. This is strong evidence of real sector DMA, although v4 did
not inspect the actual first or last eight bytes of the 512-byte target.
Its UART output then stopped midway through `P0_IRQTEST` with no later output.

V5 corrects the inspected DMA address to `0x3006E0D8` and places eight-byte
guards before and after the 512-byte target. It reports the first and last
words, changed-byte count, and guards. It then completes IDENTIFY with both
port and global IRQ routing enabled while the CPU IRQ mask remains set. The
UART reports `PxIS`, `PxIE`, global pending, SCTLR, and the IDENTIFY word. Only
if the expected global pending bit is present does it print a complete marker,
drain UART, and unmask the CPU IRQ. The handler masks the global source and
records the state; the main loop reports and acknowledges it. A board run is
The board capture validates this basic IRQ path: global pending bit 0 was
present, the open handler ran once, and mainline code acknowledged the
completed IDENTIFY. Load and error paths remain untested.
The reset stub records the loader's SCTLR and clears its high-vector bit so
CPU exceptions use the open table at address zero; the IRQ diagnostic prints
both the incoming and active SCTLR values.

The offline check verifies that execution stays within the open code,
checks the entry snapshot against board captures, compares the PUNIT write
prefix and selected controller register values at IDENTIFY issue with the
stock run, and exercises the passive snapshot with independently seeded MMIO
values. It cannot establish that READ DMA EXT or the one-shot IRQ will
complete on actual silicon: those results remain synthetic in the fixture.
V2's and V4's mid-line stops suggest an IRQ issue. V5 keeps CPU IRQs masked
through all three commands and prints the pending source before unmasking.
This stage does not perform a hardware SRST, initialize all PHYs,
expose an AHCI controller to PCIe, or preserve RAID/HyperDuo/Option ROM
behavior. The SPI output remains hybrid because it retains the stock loader
and other segments. See the v5 board capture in
[hardware-baseline.md](hardware-baseline.md).

V6 preserves the v5 SATA/IRQ diagnostic and starts a resident
[UART monitor](uart-monitor.md) afterward. It can read selected host registers
and upload CRC-checked diagnostic code into SRAM. Its provided host probe is
read-only. This avoids another SPI flash for each later host-register study,
once the monitor's receive and RAM-execution paths work on the board.
